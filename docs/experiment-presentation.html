03 · Decisions that shape the experiment

Each choice protects a different part of the question

Primary design choices define the evaluation. Robustness and feature ablation are later sensitivity views, not substitutes for the primary protocol.

DECISION 01Outer evaluation

Hold out a whole project

LOPO keeps every row from one project on the test side, then repeats until each of 39 projects has been held out once.

Reason → consequence

Random row splits can place classes from the same project in train and test. LOPO makes the held-out project unseen during model fitting and preprocessing.

DECISION 02Primary model

Use a fixed Random Forest

Tree ensembles can represent nonlinear boundaries and feature interactions without standardizing metrics.

200 treesmax_features=sqrtclass_weight=Noneseed=42n_jobs=-1
Reason → consequence

The configuration is a reproducible baseline, not a tuned or optimal model. A DummyClassifier(strategy="most_frequent") provides the majority-class reference.

DECISION 03Preprocessing

Fit imputation inside each fold

Median values are learned from the 38 training projects and reused for the held-out project.

Reason → consequence

Using held-out values to fit preprocessing would let test-project information affect the model pipeline. A predictor entirely missing in a training fold is dropped for that fold.

DECISION 04Sensitivity views

Keep the baseline and follow-ups distinct

Dummy, robustness, and feature-ablation runs answer different questions around the primary Random Forest.

Reason → consequence

The Dummy baseline checks value beyond the majority label. Robustness summarizes project and version performance; ablation probes sensitivity to selected predictors. Neither establishes causality.

Why no scaling?

The configured Random Forest uses tree splits and the implemented pipeline has no scaler. Scaling is unnecessary for this selected model.

Method boundary

LOPO evaluates unseen-project transfer in this dataset; it does not demonstrate future-version prediction or external-dataset generalization.

05 · Engineering choices and remaining limits

Reliability comes from the details around the model

These safeguards are visible in the implementation and tests; they reduce specific risks without resolving the dataset’s open questions.

Class balance

92% buggy rows

Accuracy can look strong when the majority class dominates.

Response

Compare against the most-frequent Dummy baseline and report MCC, recall, specificity, balanced accuracy, and confusion counts.

Missing values

Missingness changes by fold

Some selected predictors are missing, and a feature can be entirely empty in a training fold.

Response

Fit median imputation on training data only; record and drop features with no training values for that fold.

Project size

10 to 23,058 rows

Project size varies greatly, so pooled row metrics and equal-project macro means answer different questions.

Response

Retain version support, project summaries, and equal-project macro results as separate views.

Degenerate MCC

Some groups lack two classes

MCC cannot provide an informative two-class score when actual or predicted labels contain only one class.

Response

Status fields distinguish “Not informative” from “Undefined”; those values are excluded from MCC averages.

Prediction trace

Repeated keys can collide

Project–Version–Class combinations repeat, so those fields do not uniquely identify each source row.

Response

Alignment checks compare duplicate counts and actual labels, but saved predictions lack a stable source-row identifier.

Reproducibility

Artifact metadata is incomplete

The investigation found no dataset checksum in run metadata; the workbook lists the scikit-learn version as “Not recorded.” The protocol also calls for a separate all-data model, but no corresponding run script is present.

Response

Run configuration and fold settings are saved. Add a checksum, software version, and stable row IDs to future runs.

Tested invariants in the suite

Tests cover disjoint project folds, one test prediction per observation, training-only imputation, feature drop behavior, duplicate-aware prediction alignment, confusion counts, metric aggregation, and workbook structure. This presentation review did not rerun the Python suite.

06 · Read every score at the right level

MCC is the anchor; aggregation defines the question

Accuracy alone is not enough under strong imbalance. Support and grouping rules travel with each reported metric.

Accuracy

Share of all observations classified correctly.

Precision

Of classes predicted buggy, the share that are buggy.

Recall

Of truly buggy classes, the share identified.

F1

Harmonic mean of precision and recall.

MCC · primary

Combines all four confusion outcomes; useful when classes are imbalanced.

−1 disagreement0 no correlation+1 perfect
LEVEL 01Project–version metricsAccuracy, precision, recall, F1, MCC, support and TN / FP / FN / TP.
LEVEL 02Project summaryUnweighted version means; support-weighted alternatives; MCC from summed counts.
LEVEL 03Macro across projectsEach project contributes equally. MCC averages include informative projects only.
Unweighted across versions

Average the metric values for each version with equal weight. It describes the typical version within that project.

Support-weighted across versions

Weight each version’s metric by the number of classes in that version. Larger versions influence the project result more.

Project-pooled MCC

Sum TP, TN, FP, FN across a project’s versions, then calculate MCC from those counts.

Workbook boundary: its “Pooled MCC” is calculated within each project and then macro-averaged across informative projects. The workbook has no single all-observation pooled MCC row. The protocol describes an overall pooled comparison, so this remains an implementation/reporting gap.

Precision, recall and F1 use zero_division=0. For MCC, an actual one-class group is “Not informative”; if predictions contain one class while actual labels contain both, MCC is “Undefined.” The numeric fallback is not treated as a meaningful zero in summaries. src/evaluation/metrics.py · src/evaluation/workbook_generator.py · docs/experiment-protocol.md

08 · Investigation · no shortcut conclusion

High performance is a finding to explain

The review found no confirmed direct target leakage in the configured feature list or target-building path. It did find patterns that deserve follow-up.

Reviewed code

No direct leakage identified

bugs creates the target but is not in the 18-feature list. The LOPO implementation groups by Project; the median imputer is fitted on training data only. This does not rule out indirect effects or dataset construction issues.

Descriptive association

Some metrics track the label strongly

Directional ROC AUC: loc 0.9474, noc 0.9458, ca 0.8886, ce 0.8736. No single feature achieved perfect threshold separation. Association alone is not evidence of leakage.

Unresolved data integrity

Versions and repeated records

6,369 rows have no version value. There are 1,702 repeated (Project, Version, Class) keys (5,504 row occurrences), all among missing-version rows; eight keys have conflicting labels. Provenance is needed before deciding whether these are legitimate snapshots or duplication.

09 · Proposed next phase · not yet run

Three investigations can explain what the score is measuring

These priorities come from the read-only investigation report. They are proposed work, not completed results.

Priority 1

Measure feature-vector overlap

For each held-out project, separate test rows whose exact 18-feature vector is present in training from rows with no such match.

  • Compare support and performance by group.
  • Summarize overlap within each held-out project.
  • Preserve the original run as the reference.
Question: How much performance comes from feature vectors already seen in other projects?
Priority 2

Resolve duplicates and provenance

Investigate repeated class keys, conflicting labels, missing versions, and the undocumented index-like field.

  • Seek authoritative source documentation.
  • Determine what repeated rows represent.
  • Do not delete or deduplicate without a separate rationale and evaluation.
Question: What does each row represent, and which repeated records are legitimate?
Priority 3

Extend robustness if indicated

Review project and class outcomes, feature-importance diagnostics, and the documented ablation results before choosing new runs.

  • Test only justified feature configurations.
  • Compare with the unchanged RF and Dummy reference.
  • Keep any new experiment in a separate output directory.

10 · Takeaways · from baseline to explanation

The next research question

How much of the score survives when the features are truly new?

That answer will help distinguish cross-project transfer from repeated representations in the current dataset.

  1. Separate projects, not just rows.LOPO tests a held-out project within this dataset; it is the right boundary for the stated cross-project question.
  2. Fit preprocessing on training projects only.Fold-local imputation limits information flow from the held-out project into the fitted pipeline.
  3. Read metrics with class balance and aggregation.Accuracy, F1, MCC, version summaries, project macros, weighted means, and pooled counts answer different questions.
  4. Excellent results still need an explanation.No direct target leakage was identified, but feature overlap, repeated observations, missing versions, and provenance remain open.
  5. Keep the evidence auditable.Record checksums, software versions, and stable row IDs; preserve the original run while testing new hypotheses.
Where the work stands
